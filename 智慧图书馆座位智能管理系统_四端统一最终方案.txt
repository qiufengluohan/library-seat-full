============================================================
一、文档定位
============================================================

本方案作为毕业设计后续实际开发的“唯一总方案”。

原有四份方案分别为：
1. 设备端方案_OneNET版.txt
2. 云端接入方案_OneNET版.txt
3. 小程序端方案_OneNET版.txt
4. 图书馆智慧座位系统_精简版_Web管理端方案(1).txt

本方案将四端统一为一套技术路线、数据模型、状态机、接口命名和开发顺序。

系统最终目标不是做成商业级智慧图书馆平台，而是完成一个：
“硬件感知 + 物联网通信 + 云端业务处理 + 微信小程序 + Web管理后台”
的完整本科毕业设计。

核心闭环：

FSR402 + HC-SR501
        ↓
STM32F103C8T6
        ↓ UART
ESP8266
        ↓ MQTT
OneNET
        ↓ HTTP推送
Spring Boot
        ↓
MySQL
        ↓
WebSocket
   ↙         ↘
微信小程序    Web管理端

最终只围绕四个核心亮点展开：

1. FSR402 + HC-SR501双传感器融合，减少假占座误判
2. STM32 + ESP8266 + MQTT + OneNET完整物联网链路
3. RFID自动签到
4. Spring Boot + WebSocket实现小程序和管理端实时同步

============================================================
五、最重要的统一原则：设备状态和业务状态分开
============================================================

这是整个项目最容易写乱的地方。

设备上传的是“原始/设备数据”。

例如：

pressure_adc = 2450
pir_state = true
alarm_flag = false
online = true

但是前端不应该自己根据ADC判断“有人/无人”。

Spring Boot根据设备数据 + 预约数据 + RFID签到结果生成：

业务座位状态。

最终统一定义：

FREE       = 0   空闲
RESERVED   = 1   已预约/待签到
USING      = 2   使用中
AWAY       = 3   暂离
ALARM      = 4   异常告警

设备离线不是新的业务状态，而是：

online = false

因此前端显示：

业务状态 + 在线状态 + 告警状态。


============================================================
六、座位状态机——四端必须完全按照这一套写
============================================================

状态：

FREE
  ↓ 预约
RESERVED
  ↓ RFID签到
USING
  ↓ 暂离
AWAY
  ↓ 回座
USING
  ↓ 离座
FREE


异常流程：

USING
  ↓ 压力存在 + PIR持续异常
ALARM
  ↓ 人员回座/管理员消警
USING


超时流程：

RESERVED
  ↓ 超过签到时间
FREE

AWAY
  ↓ 超过暂离时间
FREE


取消：

RESERVED
  ↓ 学生取消
FREE


强制释放：

RESERVED / USING / AWAY / ALARM
  ↓ 管理员强制释放
FREE


重要规则：

1. “预约”由Spring Boot改变业务状态
2. “签到”由RFID事件触发
3. “暂离/回座/离座”由学生端操作触发
4. “假占座”由设备端传感器融合触发
5. “超时释放”由Spring Boot定时任务触发
6. “最终状态”统一由Spring Boot决定
7. 小程序和Web只显示Spring Boot给出的状态

============================================================
十、防假占座算法——最终只保留简单版本
============================================================

定义：

PRESSURE_THRESHOLD

例如：

pressure_adc > PRESSURE_THRESHOLD

表示座位受到明显压力。

正常情况：

压力 > 阈值
+
PIR检测到人体

=> 正常有人使用


异常情况：

压力 > 阈值
+
PIR持续没有人体

=> 疑似物品占座

持续达到设定时间：

=> fake_occupy
=> alarm_flag = true
=> 蜂鸣器报警
=> OLED提示
=> 上报云端


不要把复杂算法放到本科毕设里。

只需要做：

压力阈值
+
PIR状态
+
时间窗口

即可形成“多传感器融合算法”。

时间窗口例如：

3分钟

最终通过实验确定。


============================================================
十一、设备端不要做复杂任务系统
============================================================

不使用FreeRTOS。

STM32F103C8T6完全可以采用：

while(1)

循环执行：

1. 采集传感器
2. 判断状态
3. RFID扫描
4. OLED刷新
5. MQTT数据发送
6. 检查网络
7. 处理报警

使用简单的millis/tick时间判断，不要大量delay阻塞。

============================================================
十四、设备在线/离线
============================================================

设备：

有状态变化立即上报。

没有状态变化：

每60秒发送一次心跳。

心跳至少包含：

device_id
timestamp
online=true

Spring Boot根据：

last_report_at

判断设备是否在线。

例如：

超过设定时间没有收到数据：

online=false

前端显示：

“设备离线”

不要让小程序或Web自己判断在线。


============================================================
十五、设备离线容错——最终简化
============================================================

开题报告提出了：

STM32 SRAM环形缓存
+
ESP8266自动重连
+
恢复后补发。

最终实施建议：

保留“简单离线重连”。

不做复杂历史缓存系统。

设备断网：

1. ESP8266自动重连
2. STM32继续运行本地传感器
3. 恢复后重新连接MQTT
4. 上报最新状态
5. 云端以最新状态为准

如果有足够时间，可以增加一个很小的状态缓存。

但不要为了“最终一致性”设计复杂消息队列。

“系统在原方案中考虑Redis用于超时任务与缓存，但结合毕业设计规模，最终采用Spring Boot定时任务实现，降低系统复杂度。”

开题报告提到过。

最终不用。

OneNET本身承担物联网平台和MQTT接入。

不要做完整历史缓存系统。


4. 高并发

不做真正数百/上千设备压力系统。

可以做：

少量模拟设备 + JMeter简单测试。

论文中报告实际测试结果。

四十七、最终结论
============================================================

这套系统不再追求“功能越多越好”。

毕业设计真正需要证明的是：

1. 能采集数据
2. 能进行传感器融合
3. 能联网
4. 能使用MQTT
5. 能接入OneNET
6. 能进入Spring Boot
7. 能保存MySQL
8. 能进行预约和状态管理
9. 能RFID签到
10. 能WebSocket实时同步
11. 能在小程序操作
12. 能在Web管理
13. 能完成异常处理
14. 能完成测试和实验

只要上述闭环全部跑通，本项目已经足够形成完整的物联网工程技术本科毕业设计。

后续写代码时，严格以本文件为准。
如果旧方案与本文件冲突，以本文件为准。

开发原则：

“先跑通，再优化；先完成核心闭环，再增加展示效果；能用简单方案解决的问题，不使用复杂架构。”
